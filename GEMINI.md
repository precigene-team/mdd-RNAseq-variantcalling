# Collaboration & Operational Protocol

This file defines the operational and safety principles for this repository. To prevent context drift and ensure architectural consistency, Antigravity **MUST** adhere to the **Three Sources of Truth**.

---

## 🏛️ The Three Sources of Truth

1. **[CONTEXT.md](CONTEXT.md)**: The **Strategic & Narrative Truth**. Contains project state, clinical/biological narratives, and the analysis roadmap.
2. **[GEMINI.md](GEMINI.md)**: The **Operational Truth**. Contains protocols, safety rules, and pipeline execution standards.
3. **[README.md](README.md)**: The **Technical Truth**. Contains directory architecture, script inventories, and environment setup guides.

## 🤝 Core Collaboration Rules

* **Step-by-Step Execution**: **NO** actions will be taken beyond the currently agreed-upon step.
* **Verification**: Each step **MUST** be verified by the USER before moving to the next.
* **User-Led Progression**: **NEVER** proactively run commands or request to move to the next phase without explicit user confirmation.
* **Link Formatting**: **NEVER** use `file:///` URIs in markdown files inside the repository. Use relative paths `[Label](Path)` for local links.
* **Pattern Matching & Structural Consistency**: **BEFORE** creating any new script, Antigravity **MUST** read existing scripts in the same or related modules to mirror established pathing conventions, error handling, and logical structures internally across all pipeline modules.

---

## 🔬 Scientific Rigor & Counter-Challenge

* **Anti-Syncopation**: Antigravity **MUST NOT** automatically agree with the USER's analytical designs if they compromise statistical power or biological validity.
* **Mandatory Counter-Proposals**: If a requested method (e.g., extreme stratification or subsetting) risks producing underpowered models due to low sample size, Antigravity **MUST** explicitly challenge the design and provide a mathematically sound alternative backed by data or literature.
* **Evidence-First**: Every analytical pivot **MUST** be justified by data audits (e.g., sample counts, feature distribution) rather than simple user preference.
* **Reasoned Fixes (Anti-Panic)**: When corrected, criticized, or when a discrepancy is identified, Antigravity **MUST NOT** reactively make edits or modifications without reasoning. Antigravity **MUST** first perform a data/literature audit, explain the underlying logic and quantitative tradeoffs, and obtain explicit user confirmation of the proposed change before modifying any files.

## 🛡️ Operational Safety

* **Restricted File Deletion**: **NEVER** use `rm -rf` on directories. All file cleanups must be surgical and verified with the USER beforehand.
* **Mamba Environment**: **NEVER** use `conda` commands. Always use `mamba` (e.g. `mamba activate mdd`) and verify the active environment is `mdd` before executing tasks. Provide execution commands for the USER to run rather than running heavy scripts automatically.
* **Research Constraints**: **DO NOT** run terminal commands for independent data verification or research unless explicitly requested as a specific step.
* **Scratch & Test Scripts**: If a script is for testing, temporary debugging, or is not in the primary pipeline, it **MUST** be written in `./scratch` relative to the workspace root. **DO NOT** use Antigravity's internal brain/scratch directories (e.g. `<appDataDir>/brain/.../scratch/`).
* **NCBI/SRA Manual Lookup**: If a task requires retrieving dataset-specific clinical metadata or supplementary files from NCBI/SRA/GEO (which often fail to resolve cleanly via programmatic AI scrapers), provide the user with clear instructions and search coordinates for manual lookup rather than relying solely on automated scripts.

## 🧬 Script Design Instructions

### 1. Header & Goal Tagging
Every script written for this repository **MUST** start with these tags in the first two lines:
1. First line: Relative path tag, e.g. `# [[01_core_alignment/01_raw_fastqc.sh]]`
2. Second line: Goal tag, e.g. `# Goal: Run FastQC on raw fastq files.`

### 2. Dynamic Pathing Setup
Avoid hardcoded absolute paths. All scripts must dynamically resolve the project root by climbing the directory tree looking for a `run` orchestrator or using relative shell pathing:
```bash
export PROJECT_ROOT="${PROJECT_ROOT:-$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)}"
```

### 3. Standardized Output Architecture
* **User-Facing Results**: Save categorized results to:
  * Tables: `results/tables/{2-digit_prefix}_{filename}`
  * Figures (plots, HTML widgets, maps): `results/figures/{2-digit_prefix}_{filename}`
* **RData / RDS Objects**: Save intermediate serialization objects to `_data/RData/{module_name}/{2-digit_prefix}_{filename}`.
* **Filename Consistency**: Prefix all outputs (including tables, figures, and RData) with the 2-digit number of the generating script (e.g., `01_annotated_counts.csv` generated by script `01_gene_mapping.R`).

### 4. Step-by-Step Documentation & Data Assertions
* **Sequential Step Headers**: Every script must contain a block at the top outlining its execution steps sequentially (similar to `gene_map.R` design):
  ```R
  # Steps:
  #   1. Read raw expression matrix and metadata
  #   2. Clean Ensembl IDs and collapse duplicates...
  ```
* **Data Assertions**: Implement strict data assertions (e.g., matching row counts, confirming row uniqueness, checking for NAs in factor columns) immediately after any merge, group-by, or collapse operations to guarantee data integrity before proceeding.

### 5. HPC Operations (HPC-01)

* **Job Submission**: Use `sbatch` for heavy loads; negligible loads can use direct bash.
* **Package Management**: **DO NOT** automate installations. Notify the user if a dependency is missing.
